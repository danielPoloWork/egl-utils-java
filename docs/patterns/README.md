# Design Patterns Catalogue

Living index of every design pattern **adopted**, **planned**, **considered and rejected**,
or **under evaluation** for `egl-utils-java`. Mandatory reading whenever a PR introduces
or removes a pattern, and updated in the same PR.

- **Rules** — [`AGENTS.md`](../../AGENTS.md) §8.
- **Canonical taxonomy** — [`design-patterns.md`](design-patterns.md). All pattern names
  used here, in ADRs, and in commit messages must match its spelling and categorisation.

## Architecture style

_No single architectural style committed at intake (typical for a library, which exposes an API
rather than an application architecture). Record one in an ADR here if that changes._


## How to use this catalogue

- **Adding a pattern** — when a PR lands one, add a row to *Implemented / Planned* as
  `Implemented`, with the ADR link and the code location (a real path under
  `src/main/java/...`); a pattern decided in an ADR but not yet in code is added as `Planned`.
- **Refining** — update the row and link the new ADR.
- **Rejecting** — add it to *Rejected* with the reason; do not silently drop it.
- **Removing** — move the row to *Superseded*, link the superseding ADR, keep the history.

Status vocabulary: `Planned` (decided in an ADR, not yet landed) · `Implemented` (present
in `src/main/...`, ADR `Accepted`) · `Considered` · `Rejected` · `Superseded`.

## Rejected

| # | Pattern | Considered for | Rejected because | ADR / PR |
|---|---------|----------------|------------------|----------|
| 1 | Visitor | FR-16 `AuditLog` — walking a host's object graph to capture before/after state | Classic Visitor requires the visited structure to cooperate: an `accept(Visitor)` method on every audited type. A library cannot ask a consumer's domain objects to implement its interface in order to be auditable, and an audit trail that only works on types written after the library arrived is not one. The **intent** — add an operation to an object structure without changing it — is met by a reflective walk over public accessors instead, which is the same goal reached without the contract. Recorded rather than silently skipped, because the traversal in `AuditLog.collect` reads like a Visitor and the next reader should know why it is not one | [ADR-0022](../adr/0022-redact-at-capture-behind-a-typed-event.md) |
| 3 | Specification | FR-07 `PageRequest.validatedAgainst` — deciding whether a client-supplied sort property is one the repository permits | The **intent** is a near miss and the shape is not: Specification's value is that predicates *compose* — `and`, `or`, `not`, reusable business rules assembled into a selection criterion — and row 8 already uses it for `AuditPolicy`, where the never-capture list genuinely composes by union and can be extended, read back and tested as a value. FR-07's check is a single `Set.contains` against a set supplied per call, with nothing to compose it with and nothing to name it as. Adopting the name would send the next reader looking for a predicate algebra that does not exist, and would make the catalogue's one real Specification harder to recognise by putting a set-membership test beside it. AGENTS.md §8.1 forbids the force-fit, §8.3 asks for the reason, and the honest one is that the interesting decision here was *where the check may be reached from* (ADR-0033), which is encapsulation rather than a catalogued pattern | [ADR-0033](../adr/0033-publish-no-accessor-for-the-unvalidated-sort.md) · [RFC-0003](../rfc/0003-jdbc-and-json-contracts.md) |
| 4 | Decorator | FR-08 `ManagedThreadPool` — an `ExecutorService` wrapping a `ThreadPoolExecutor` and changing what `close()` does | The **structure** is Decorator's exactly — same interface, holds a delegate, alters one operation — and the **intent** is its opposite, which is why recording it beats adopting it. A Decorator exists so responsibilities can be **composed at run time**, stacking wrappers a caller chooses; here there is exactly one wrapper, it is not composable, it is `final` so nothing can extend it, and the caller never selects it. Worse, Decorator **adds** behaviour to a subject the caller still holds, whereas this type's whole purpose is that the subject is **unreachable**: it exists to withhold `setCorePoolSize`, `setRejectedExecutionHandler` and `getQueue`, so a reader told "Decorator" would go looking for the wrapped executor they are meant not to have (ADR-0022's rule, applied structurally). Facade was considered second and fits no better — a Facade publishes a *new, simpler* interface, and this one publishes the same `ExecutorService` a caller already knows. AGENTS.md §8.1 forbids the force-fit and §8.3 asks for the reason; the reason is that the interesting property here is subtractive, and the taxonomy has no name for a wrapper that exists to take surface away | [ADR-0035](../adr/0035-declare-autocloseable-so-the-override-is-legal.md) · [RFC-0004](../rfc/0004-concurrency-contracts.md) |
| 6 | Strategy | FR-11 `JwtTokenProvider` — selecting the signing/verification algorithm | **The one place in this repository where the obvious pattern is the vulnerability.** Strategy's intent is to make an algorithm interchangeable at run time, and a JWS token carries its algorithm in a header field the *attacker writes*. A verifier built as a Strategy — read `alg`, look up the matching verifier, apply it — is precisely the algorithm-confusion attack: hand it an HS256 token signed with the issuer's RSA **public** key and it computes HMAC-SHA256 with a key the attacker also has, and the token verifies. `JwtNegativeTest` forges exactly that token and shows it verifying against a naive verifier holding the same bytes. So the algorithm is fixed at **construction**, the header is *compared* against it and never consulted to select anything, and one verifier accepts exactly one algorithm (ADR-003). Catalogued here because a reader who knows the pattern will wonder why it was not used, and the answer is worth more than the adoption would have been: **interchangeability chosen by untrusted input is not a pattern, it is a hole** | [ADR-003](../../.spec/adr/d4np_java_adr_003_jwt_library.md) · [RFC-0005](../rfc/0005-security-contracts.md) |
| 5 | Leader Election (Cloud & Distributed) | FR-10 `DistributedLock` — the interface, and the fencing token that makes a lease safe | The **nearest neighbour in the taxonomy**, recorded because the relationship explains the design better than anything else does and a reader will otherwise ask. Leader Election *elects a coordinator and gives it a term*; the number it hands out — Raft's term, ZooKeeper's epoch — is the same idea as `LockHandle.fencingToken()`, and for the same reason: a deposed leader and a stale lock holder are the same failure, and both are fixed by making the resource reject the lower number. **It is still not this pattern.** `DistributedLock` elects nobody, holds no term, has no notion of peers and no membership; it is the *primitive* leader election is usually built from, and a consumer wanting an election writes it on top rather than receiving one. Adopting the name would promise a coordinator this interface never produces. AGENTS.md §8.1 forbids the force-fit and §8.3 asks for the reason; §8.4 asks the category to be scanned first, and Cloud & Distributed's other nine entries — Circuit Breaker, Bulkhead, Saga and the rest — are further away still | [ADR-0037](../adr/0037-a-fencing-token-that-restarts-is-worse-than-none.md) · [RFC-0004](../rfc/0004-concurrency-contracts.md) |
| 2 | Message Translator (EIP) | FR-21 `ObjectMapperExtensions.convert` — deep conversion between two POJO shapes | The **intent** matches almost exactly — transform a representation between schemas — and the name is still wrong here, so it is recorded rather than adopted. Message Translator is an integration pattern: it presumes a message, a channel and an endpoint, and its value is that the translation is a routable step a pipeline can compose. `convert` is an in-process call between two of the caller's own types, with no message, no channel and nothing to route; naming it Message Translator would put integration vocabulary on a two-argument static method and invite a reader to look for the pipeline it belongs to. AGENTS.md §8.1 forbids the force-fit, and §8.3 asks for the reason — this is it | [ADR-0026](../adr/0026-rewrite-jacksons-unchecked-conversion-failure.md) · [RFC-0003](../rfc/0003-jdbc-and-json-contracts.md) |

## Candidate patterns to consider

The taxonomy in [`design-patterns.md`](design-patterns.md) lists every pattern in scope. As
the architecture takes shape, narrow that universe to the patterns plausibly applicable to
*this* artifact and list them here by category, each with a one-line "possible application".
A candidate remains a candidate until adopted (own ADR) or explicitly rejected.

## Out-of-scope categories

Record here any taxonomy category pre-classified as not applicable to this artifact (with a
one-line reason), so the policy of explicit rejection is honoured without filling the
*Rejected* table with N/A noise.
