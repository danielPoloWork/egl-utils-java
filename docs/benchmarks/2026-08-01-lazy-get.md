# Benchmark Report: `Lazy.get()` steady state — the NFR-01 budget

- **Date:** 2026-08-01
- **Version / commit:** v0.1.0 + ROADMAP item 2.2 (`feat/lazy-safe-publication`)
- **Environment:** Intel Core i5-6600K @ 3.50 GHz (4 cores, no SMT), 32 GB RAM, Windows 10 Pro
  19045, Temurin **17.0.20+8** and **21.0.12+8**, Maven 3.9.9, `--release 17`
- **Command:** `mvn -B -Pjmh verify` (PR-grade defaults: 1 fork, 1 warmup iteration, 1 measurement
  iteration of 1 s)

> **Informational, not a gate.** One fork and one iteration on a developer workstation proves the
> harness executes and puts the result in the right order of magnitude; it is not the 5x10 run on the
> named reference machine that spec §6 requires. RFC-0001 states the same caveat as a known risk, and
> **ROADMAP item 8.3 owns making NFR-01 an absolute CI gate** — until it lands, this number is tracked
> on the reference machine and advisory in CI.

## Scenario

`LazyGetBenchmark.steadyStateGet` (`d4np-core/src/bench/java/it/d4np/utils/`) times `Lazy.get()` on an
**already-initialized** instance in `AverageTime` mode, nanoseconds. That is the path NFR-01 budgets:
one `volatile` read of the memoized value plus a branch, no lock and no allocation.

It runs in the **same JMH invocation** as item 1.8's `PublicationBaselineBenchmark`, which is the point
of reading the three numbers together:

- `volatileRead` — a bare `volatile int` read; the **floor** this budget is made of;
- `finalRead` — the same access with no publication guarantee, for scale;
- `steadyStateGet` — the real call.

`steadyStateGet` minus `volatileRead` is what `Lazy` costs over the field access it wraps. If that
delta were large, `get()` would not be inlining — which is the specific thing
[ADR-0013](../adr/0013-lazy-initialization-by-double-checked-volatile.md) keeps the slow path in a
separate method to protect.

The value is returned rather than stored, so JMH consumes it and dead-code elimination cannot delete
the read; a `volatile` read cannot be hoisted out of the loop or constant-folded even though the
initializer is trivial, which is why the budget can honestly be stated against `() -> "value"`.

## Results

| Metric | Temurin 17 | Temurin 21 | Spread |
|--------|-----------|-----------|--------|
| **`LazyGetBenchmark.steadyStateGet`** | **0.827 ns/op** | **0.945 ns/op** | n/a — single iteration, no error estimate |
| `PublicationBaselineBenchmark.volatileRead` | 0.606 ns/op | 0.552 ns/op | n/a |
| `PublicationBaselineBenchmark.finalRead` | 0.481 ns/op | 0.626 ns/op | n/a |

**NFR-01 budget: ≤ 2 ns/op. Measured: 0.827 (17) and 0.945 (21).**

## Interpretation

**The budget is met with roughly 2x headroom on hardware slower than the spec's reference machine**
(Ryzen 7 5800X), on both toolchains. This is the first NFR in the project closed by a measurement
rather than an assertion.

The delta over the bare volatile read is **0.22 ns/op on 17 and 0.39 ns/op on 21** — sub-nanosecond,
i.e. a small number of cycles. That is the signature of an inlined `get()`: what remains is the field
read plus the null branch, with no call overhead. A delta in the several-nanosecond range would have
meant the method was not inlining and would have sent the design back to ADR-0013's fast/slow split.

Two honest caveats about the *spread*, both inherited from item 1.8's baseline report and unchanged
here:

- **The numbers are near JMH's noise floor and the iteration count cannot resolve differences this
  small.** `finalRead` lands *above* `volatileRead` on JDK 21 (0.626 vs 0.552) and *below* it on JDK
  17 (0.481 vs 0.606) — the ordering inverts between toolchains, which is what a single 1-second
  iteration looks like at this magnitude. Read the three numbers as "all in the same half-nanosecond
  band", not as a ranking.
- **On x86-64 a volatile *read* needs no fence**, so the small delta is also the theoretically
  expected result. A weakly-ordered platform (aarch64, ppc64le) would separate these numbers, and is
  the same platform gap ADR-0013 records for the jcstress side.

Because of both, the *conclusion* drawn here is deliberately weak and robust: **`Lazy.get()` is within
NFR-01's budget by a margin far larger than the measurement error**, which is a claim one iteration can
support. Ranking the three benchmarks against each other is not.

## Reproduce

```bash
# From a clean checkout, with JAVA_HOME on Temurin 17 or 21:
mvn -B clean
mvn -B -Pjmh verify -pl d4np-core
cat d4np-core/target/jmh-result.json

# Publication-grade, on the reference machine (spec §6: 5 forks x 10 iterations):
mvn -B -Pjmh verify -pl d4np-core -Djmh.forks=5 -Djmh.warmup.iterations=10 -Djmh.iterations=10
```
