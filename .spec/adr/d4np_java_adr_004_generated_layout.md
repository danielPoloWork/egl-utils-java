# ADR-004: Generated repository layout — reconciling the EADOS flat source tree with the Maven reactor

## Context

[ADR-001](d4np_java_adr_001_module_split.md) committed this project to a **nine-artifact Maven reactor** (`core`, `jdbc`, `concurrent`, `security`, `json`, `spring-adapter`, `lock-redisson`, `test`, plus `bom`), and made framework independence a *build* property enforced by maven-enforcer rather than a review convention.

This repository is generated by EADOS, whose renderer emits exactly **one** source tree per manifest, derived as `src/<kind>/<lang>/<group_path>/<project_slug>`. With the settled manifest values that is:

```
src/main/java/it/d4np/util        (mirrored at src/test/… and src/bench/…)
```

Maven's contract is that every module is its own directory with its own `pom.xml` and its own `src/main/java`. Consequently `src/main/java/it/d4np/util/core` is a **package**, not a module — the reactor cannot be expressed inside a single rendered tree.

The two are therefore not merely inconvenient to reconcile; rendering the flat tree as-is would produce **one artifact whose packages are named after the intended modules**. That is structurally identical to ADR-001's rejected Option B and to the v1 monolith the entire specification exists to correct: the generator would silently undo ADR-001. A consumer wanting only `StrategyRegistry` would again inherit Spring, Jackson, AspectJ and Redisson.

The decision cannot be deferred past `scaffold`, because scaffold is the step that lays the tree down and drafts the bootstrap PR.

## Options considered

**A. Scaffold once as a single-artifact repo, then establish the reactor as Milestone 1 item 1.1** *(chosen)*
- ✅ Unblocks scaffold immediately, and ADR-001 survives because the reactor exists *before* any component code lands.
- ✅ The work is already scheduled and signed off — `spec.milestone1_items` carries "Maven reactor skeleton: parent POM, the nine modules from ADR-001, and the BOM".
- ✅ Keeps what EADOS actually contributes here: the governance layer (`AGENTS.md`, `docs/`, `.github/`, the CI skeleton, the frozen spec, the ADR/RFC machinery), all of which is layout-agnostic.
- ✅ Restructuring after hand-off is ordinary development, not forbidden hand-editing of generated output: control passes to the generated repository's own `AGENTS.md` once the bootstrap PR is drafted.
- ❌ Generated docs will quote `src/main/java/it/d4np/util` as *the* source root; after 1.1 the real roots are `<module>/src/main/java/it/d4np/util/<module>`. Those references must be corrected inside item 1.1 or the documentation drifts from the tree.
- ❌ The generated `consistency_lint.py` may assert the rendered paths exist; that assertion needs updating in the same item.

**B. Teach EADOS multi-artifact rendering first, then generate**
- ✅ Durable and general. The same gap affects Gradle multi-project builds, Cargo workspaces, .NET solutions, Go multi-module repos and npm workspaces — this is not a Java problem, it is a missing dimension in the factory.
- ✅ Preserves the property that a rendered repository passes its own lint out of the box.
- ❌ A genuine factory change: a `modules:` dimension in the manifest schema, new placeholders, template changes, `render.py` work, and its own EADOS ADR — and by the genericity rule it must hold for *every* language, not just Java.
- ❌ Blocks this project on unrelated upstream work of a much larger size.

**C. Render the flat tree and treat the module names as packages**
- ✅ Requires no decision and no additional work.
- ❌ Produces exactly one artifact. This *is* ADR-001 Option B, already rejected there because optional dependencies hide the real graph and the "core is clean" claim becomes unverifiable. It reintroduces the monolith by construction.

**D. One repository per module**
- ❌ Already considered and rejected as ADR-001 Option C (overkill for one team; cross-cutting refactors such as the error model touching `core` and the adapter become multi-repo choreography). It would also mean nine manifests and nine generation runs. Not reopened here.

## Decision

**Option A.** `scaffold` renders the governance layer plus a single source tree. **Milestone 1 item 1.1 then immediately establishes the reactor**: the parent POM, the nine modules from ADR-001 and the BOM, relocating the rendered tree to become the **`core` module's** source root.

Two constraints are part of this decision, not follow-up niceties:

1. **No component code (FR-01 onward) is committed before the reactor exists**, so ADR-001's dependency rules are enforceable from the very first component commit.
2. **Item 1.1 also updates every generated reference** to `src_main` / `src_test` / `src_bench` and the `consistency_lint.py` path assertions. A milestone that leaves those stale is not done.

Option B is raised separately as an upstream EADOS RFC. **This project does not block on it.**

## Consequences

- **Hard ordering constraint:** item 1.1 is a prerequisite for Milestone 2. Component code committed before the reactor exists would land in the wrong artifact and have to be moved.
- `maven-enforcer` and `japicmp` are inherently per-module, so NFR-08 (dependency policy) and NFR-09 (binary compatibility) — and roadmap item 8.1 — are all downstream of 1.1. Until the reactor exists, the "framework independence is CI-enforced" claim is aspirational.
- The manifest's `src_main` stays `src/main/java/it/d4np/util` and is to be read as **the `core` module's package root**, not the repository's only source root. The manifest is not wrong; its scope is narrower than it appears.
- Dependabot with `package_ecosystem: maven` resolves a reactor from a single root entry, so no per-module configuration is required.
- If the upstream RFC lands, this project may migrate its layout to the generated form and **this ADR is superseded** rather than amended.
- File naming: this ADR keeps the `d4np_java_adr_00N_` convention of its three siblings for consistency. All four normalise to `docs/adr/000N-*.md` when scaffold moves them into the generated repository.
